# UI Walkthroughs

Figma-style storyboards generated by Playwright. Each walkthrough
records a UI workflow as a sequence of steps with screenshots,
annotations, and the console / network / JS errors that fired along
the way. Outputs are an interactive `report.html` plus a full-page
`report.png` for VSCode inspection.

## Quick start

```bash
# 1. Backend up + auth bootstrapped
bash scripts/dev-local-pdf.sh                               # in repo root
query-eval segment auth init --tenant-slug default \
  --tenant-name "Default" --admin-username admin --admin-password admin

# 2. Vite dev server (separate terminal)
cd frontend && npm run dev

# 3. Run the walkthrough (separate terminal, frontend/ cwd)
npm run walkthrough login-and-tenant-admin
```

The runner opens a real Chromium window (headed by default), walks
through the flow, then prints the report paths:

```
[walkthrough] data:   tests/walkthrough/output/login-and-tenant-admin_2026-…/data.json
[walkthrough] HTML:   tests/walkthrough/output/login-and-tenant-admin_2026-…/report.html
[walkthrough] PNG:    tests/walkthrough/output/login-and-tenant-admin_2026-…/report.png
```

Open the HTML in a browser for the interactive view, or open the PNG
in VSCode's image preview for an at-a-glance inspection.

## Flags

```bash
npm run walkthrough <flow> -- --headless          # run hidden (CI-style)
npm run walkthrough <flow> -- --base-url http://… # point at a different host
```

## Output anatomy

Each run produces a fresh timestamped directory under
`tests/walkthrough/output/`:

```
<flow>_2026-05-13_…/
├── screenshots/
│   ├── 01_01.png         step 1, screenshot 1
│   ├── 01_02.png         step 1, screenshot 2
│   ├── 02_01.png         step 2, screenshot 1
│   └── …
├── data.json             raw recording (machine-readable)
├── report.html           interactive storyboard
└── report.png            full-page screenshot of report.html
```

The HTML report shows, per step:

- **Left:** screenshots with SVG overlays — cyan highlight rectangles
  for `s.highlight(selector)`, pink arrows for `s.arrow(from, to)`,
  red banners for `s.error(text)`.
- **Right:** the action trace (`goto /login`, `click submit`, …) plus
  any console messages, network 4xx/5xx, or JS errors that fired
  during that step.

Top-of-report banner summarises the run: green when every step passed
and nothing fired in console/network/JS-errors; yellow with a count
when something needs attention.

## Adding a new walkthrough

1. Copy the template:

   ```bash
   cp tests/walkthrough/flows/_template.walkthrough.ts \
      tests/walkthrough/flows/my-flow.walkthrough.ts
   ```

2. Edit `my-flow.walkthrough.ts` — replace the example steps with
   your own. Available helpers are documented inline in the template.

3. Run it:

   ```bash
   npm run walkthrough my-flow
   ```

## Helpers cheat-sheet

```ts
// Navigation + interaction
await s.goto("/path")
await s.click("selector")
await s.fill("selector", "value")
await s.waitForUrl(/regex|substring/)
await s.expectVisible("selector")
await s.screenshot({ note?: string })

// Annotations (queued; applied to the NEXT screenshot, then cleared)
s.note("text")                         // side-panel note
s.highlight("selector", "label?")      // cyan box on screenshot
s.arrow("from-sel", "to-sel", "label?") // pink arrow
s.error("text")                        // red banner on screenshot
```

Console / network 4xx-5xx / JS errors are captured **automatically**
for the duration of each step — no setup required.

## CI / headless usage

The runner is intentionally **manual-only** for now (per design
discussion 2026-05-13). To wire it into a pre-merge job later, run
with `--headless` and capture the `output/` directory as a build
artefact. The HTML is self-contained (all paths are relative) and
opens directly in a browser.

## Limitations

- Selectors are CSS by default; for text-based matches use Playwright's
  `text=` prefix (e.g. `s.click('text=Submit')`).
- `s.highlight` / `s.arrow` resolve selectors **at screenshot time**.
  If the element has moved or unmounted by then, the overlay is
  silently dropped (the screenshot still saves).
- The runner does NOT clean up tenants or users it creates — the
  walkthrough should use timestamped slugs to avoid collisions.
